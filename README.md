### 2.3. Объяснение наблюдений

1. Для Германии ключ `(country, ended_at)` сократил отбор со 102 до 8 гранул, чтение — с 835 584 до 65 536 строк. Для всех стран ключ `ended_at` выбрал 102 гранулы и прочитал 835 584 строки, а `(country, ended_at)` — 114 гранул и 931 456 строк.

2. При `ended_at` события упорядочены по времени: оба запроса отбирают один временной диапазон. В обоих планах `PrimaryKey` использует только `ended_at`, выбирая 102 гранулы. При `(country, ended_at)` события сначала разделены по странам, затем упорядочены по времени внутри страны. Для Германии индекс использует оба поля и выбирает 8 гранул. Без фильтра страны план использует `ended_at` через `generic exclusion search`: 14 диапазонов и 114 гранул. Поэтому второй столбец ключа тоже помогает отбору, но в этом опыте читается больше гранул.

3. На `hw_events_time` Германии соответствуют 59 423 события, всем странам — 825 369. Оба запроса читают 835 584 строки: индекс отбирает одинаковые временные гранулы, а фильтр страны применяется к прочитанным данным. Подходящие события проходят условия; прочитанные строки включают остальные события выбранных гранул; итоговый отчёт содержит одну строку для Германии или семь строк для всех стран после группировки.

4. Для Германии выбираю `(country, ended_at)`: 65 536 строк и 1 179 648 байт вместо 835 584 строк и 15 040 512 байт. Для всех стран — `ended_at`: 835 584 строки и 15 040 512 байт вместо 931 456 строк и 16 766 208 байт. Для выбора ключа всей нагрузки нужны частоты разных запросов, их фильтры и периоды, требования к задержке, объёмы вставок и затраты на хранение.

Запросы: блоки `3.2.ordered` и `3.2.mixed` в [sql/03_codecs.sql](sql/03_codecs.sql). [Оба фрагмента по шесть значений](results/03_neighbors.md).

Разности рассчитаны по `seconds_from_start` (секунды):

| Порядок | Исходные значения | Первые разности | Вторые разности |
|---|---|---|---|
| Регулярный | 0, 1, 2, 3, 4, 5 | 1, 1, 1, 1, 1 | 0, 0, 0, 0 |
| Перемешанный | 36993, 222135, 480696, 440268, 486310, 296535 | 185142, 258561, -40428, 46042, -189775 | 73419, -298989, 86470, -235817 |

В регулярном ряду шаг равен одной секунде, вторые разности нулевые. В перемешанном фрагменте постоянного шага нет, знаки и величины разностей меняются.

Для восстановления перемешанного фрагмента нужны первое значение `x₀ = 36993` и первая разность `d₁ = 185142`. По первой второй разности `73419`:

- `x₀ = 36993`;
- `x₁ = 36993 + 185142 = 222135`;
- `d₂ = 185142 + 73419 = 258561`, `x₂ = 222135 + 258561 = 480696`.

Это значения в секундах от `2026-10-20 00:00:00 UTC`; для восстановления временных меток прибавляем их к этому началу.

### 3.3. Размеры колонок

Прогноз: перестановка ухудшит сжатие, особенно для Delta и DoubleDelta, поскольку нарушит регулярность соседних значений и их разностей.

SQL: блок `3.3` в [sql/03_codecs.sql](sql/03_codecs.sql). [Шесть измерений размеров](results/03_sizes.md). Несжатый размер каждой колонки — 2 000 000 байт.

### 3.4. Объяснение результатов

1. В регулярной таблице: Delta + ZSTD — **2 234 байта**, DoubleDelta + ZSTD — **2 325**, ZSTD — **1 332 284**. Минимум у Delta + ZSTD. В перемешанной: ZSTD — **1 543 831 байт**, Delta + ZSTD — **1 586 160**, DoubleDelta + ZSTD — **1 962 850**. Минимум у ZSTD.

2. Для Delta + ZSTD перестановка увеличила размер с **2 234** до **1 586 160 байт**. Регулярный ряд даёт повторяющиеся первые разности `1`, которые хорошо сжимаются; в перемешанном разности имеют разные величины и знаки.

3. Delta кодирует разности соседних значений, DoubleDelta — разности первых разностей. ZSTD сжимает полученное представление без потерь. Нерегулярные разности и служебные данные преобразований могут увеличить итоговый размер, поэтому дополнительный кодек не гарантирует улучшения.

4. Порядок влияет и на отбор гранул при чтении. В задании 2 для Германии меньше читал ключ `(country, ended_at)`, для всех стран — `ended_at`. Поэтому вместе с размером хранения нужно учитывать запросы и объём чтения.

Сохранение информации: цепочки кодеков работают без потерь, поэтому по исходным временам можно точно посчитать события за интервал 10:15–10:45. Если сохранить только дневные количества, распределение событий внутри дня теряется; точный ответ за такой интервал получить нельзя.

### 4.5. Объяснение поведения

1. При порции Б MV обработало только три вставленных события. Опоздавшее событие попало в группу 24 октября по `ended_at`, поэтому изменился итог старого часа. Историю заполняли отдельно: MV не обрабатывает строки, загруженные до его создания.

2. В target могут храниться несколько строк одной группы от разных вставок, пока фоновые слияния не объединили их. `sum` и `GROUP BY` дают полный итог независимо от слияний.

3. Для RU, 27 октября, 19:00 порция А даёт 4 события, 2 коротких и 84 секунды; вклад Б — 1 короткое событие длительностью 1 секунда. Правильная доля: `100 × (2 + 1) / (4 + 1) = 60%`; средняя длительность: `(84 + 1) / (4 + 1) = 17` секунд. Обычные средние порций дают `(50% + 100%) / 2 = 75%` и `(21 + 1) / 2 = 11` секунд. Они неверны, потому что порции имеют разное число событий.

4. Гарантированно пересчитать долю с порогом `played_seconds < 10` нельзя. Target хранит общее количество, количество событий короче 20 секунд и сумму секунд; количества короче 10 секунд в нём нет. Например, длительности `5, 15` и `10, 10` дают одинаковые сохранённые итоги, но разные доли событий короче 10 секунд.
